# Безопасность

Игра — статический сайт без собственного сервера и без базы данных. Это сильно сужает поверхность атаки:
нечего «взломать» на сервере, нет паролей, аккаунтов и персональных данных. Единственное, что приходит
извне, — сообщения соперника в онлайн-матче и данные в `localStorage` / `sessionStorage` самого браузера.
Ниже — что защищено, чем и что **осталось** (честно).

## Что защищено

### Онлайн-матч: «таможня» входящих сообщений (`src/net`)

Всё, что приходит от соперника, считается недоверенным — даже если оно пришло от настоящего клиента.

| Мера | Где | От чего |
|------|-----|---------|
| Лимит размера сообщения (64 КБ) | `limits.ts`, `room.ts` | заваливание памяти огромными данными |
| Проверка схемы: каждое поле, тип, диапазон; из присланного собирается **новый** объект | `validate.ts` | `NaN`/`Infinity`, координаты за миром, `__proto__`-загрязнение, лишние поля |
| Лимиты по типам сообщений (токен-бакет) и счётчик нарушений с временной блокировкой — **для каждого отправителя отдельно** | `limits.ts`, `room.ts` | флуд, «залипание» цикла обработки; один спамер не блокирует остальных игроков |
| Места за столом закрепляются за первым, кто их занял (`seats.ts`); моё место — только моё; во время матча сообщения принимаются только от **состава матча** (`config.ids`), место отправителя берётся из состава, а не из сообщения | `room.ts`, `seats.ts` | посторонний в комнате и самозванец на чужом месте не влияют на матч |
| `start` принимается только от места хозяина (0); игрок, которого нет в составе, в матч не входит; вход в идущий матч по `sync` — только от участника этого матча | `RoomScreen.tsx` | гость не может начать матч «за» хозяина, посторонний — затащить в «свой» матч |
| Прицел и бросок принимаются **только от того, чей сейчас ход**; ранние (у отстающего зрителя) ждут в буфере ограниченного размера и срока | `OnlineMatchScreen.tsx` | игрок не может бросить за другого или вне очереди |
| «Пропуск хода» (матч на 3–4) принимается, только если пропускаемый и по моим данным не в сети или вышел, ход действительно текущий (номер броска), а он давно молчит | `OnlineMatchScreen.tsx`, `MatchRules.ts` | «выталкивание» игрока, который в сети и думает над броском |
| Потолки записи броска: кадры, события, шаги физики, части | `throwRecord.ts` | подделанный «бесконечный» бросок |
| Выбитый асык не воскресает (`importAsyks(..., false)`) | `PhysicsWorld.ts` | возврат уже выбитых асыков |
| Строгая проверка снимка состояния (`SyncTrust` + `decideSync`): мои броски и очки неизменны; каждый другой игрок опережает меня не больше чем на один бросок (очередь по кругу); закон сохранения (выбито = убрано с поля); не более 8 асыков за бросок; счёт не уменьшается; снимок другого состава не принимается | `sync.ts` | «перемотка» матча одним поддельным `sync`, подмена чужого счёта |
| Код комнаты: 10 символов из 31, `crypto.getRandomValues` с отбрасыванием смещённых значений (31¹⁰ ≈ 8,2·10¹⁴ вариантов) | `protocol.ts` | угадывание кода комнаты перебором |
| Имена: очистка управляющих, невидимых и bidi-символов, длина до 16 | `ui/format.ts` | подмена направления текста, невидимые имена, переполнение интерфейса |
| React экранирует вывод; `dangerouslySetInnerHTML` и `eval` не используются | весь `src/ui` | XSS через имена |

### Локальное хранилище

`localStorage` (прогресс, настройки) и `sessionStorage` (комната, снимок матча) читаются защитно:
ограничение размера, `JSON.parse` в `try`, проверка типов и диапазонов, значения по умолчанию при любой
ошибке, `__proto__` не загрязняет прототипы (`storage/progress.ts`, `net/session.ts`). Подделанные данные
отбрасываются, а не ломают игру.

### Сайт и сборка

- **Content-Security-Policy** (`<meta>` генерируется при сборке, `vite.config.ts`): `default-src 'self'`,
  `script-src 'self'` (никаких inline-скриптов и `eval`), `connect-src` — только свой домен и хост Supabase
  из переменной окружения, `object-src 'none'`, `frame-src 'none'`, `base-uri 'self'`, `form-action 'self'`.
- Все шрифты — отдельные файлы (`assetsInlineLimit: 0`), поэтому `font-src 'self'` без `data:`.
- `Referrer-Policy: no-referrer` (meta): адрес комнаты не утекает на другие сайты.
- Защита от встраивания в чужую страницу (`src/main.tsx`).
- Зависимости: `npm audit` — без уязвимостей; `npm ci --ignore-scripts` в CI (скрипты установки пакетов не
  выполняются); Dependabot следит за npm и GitHub Actions.
- GitHub Actions: сторонние действия закреплены по SHA коммита, права `permissions: {}` по умолчанию и
  минимальные на каждую задачу, `persist-credentials: false`, отдельная задача `npm audit`.
- Dev-сервер по умолчанию слушает только `localhost`; доступ из локальной сети — явная команда `npm run dev:lan`.
- Секреты: в проекте используется только **publishable-ключ** Supabase (он предназначен для браузера и
  по определению виден в коде сайта). Secret / `service_role` ключ в проект не добавлять никогда. `.env`
  в `.gitignore`; в истории git секретов нет.

### Игровая логика

- Бросок разрешается только игроку, чей ход (`MatchRules.canThrow`), а онлайн — только своему месту.
- Физика детерминированно считается на устройстве бросающего; соперник проигрывает запись и принимает
  итоговое состояние, но только после проверок выше.
- Все 20 испытаний и все расстановки матча доказаны проходимыми решателем (`solvability.test.ts`), звёзды
  выставлены по достижимому максимуму; фазз-тесты физики не находят NaN, «вылетов» за мир и зависаний.

## Что осталось (честно)

1. **Изменённый клиент может мешать в своём матче.** Это игра между двумя браузерами без доверенного
   сервера, поэтому хозяин физики броска — бросающий. Проверки выше не дают подделать **чужие** очки,
   перемотать матч или сломать соперника, но злоумышленник может, например, «промазывать» или сообщать
   о своём броске правдоподобный, но нечестный результат. Для дружеской игры это приемлемо; для
   рейтинговых матчей нужен авторитетный сервер.
2. **Комната — публичный канал по коду.** Любой, кто знает код (10 символов), может подключиться к
   Realtime-каналу. Он не получит место в матче (занято двумя), а его сообщения игнорируются, но может
   видеть публичные сообщения. Код не угадать перебором, но ссылку нужно отправлять только тому, с кем
   играете.
3. **Локальные рекорды не защищены от правки.** Это `localStorage` на вашем устройстве; рейтинга нет, так
   что и обманывать некого.
4. **Заголовки ответа.** GitHub Pages не даёт настроить HTTP-заголовки, поэтому CSP и referrer задаются
   через `<meta>`, а `frame-ancestors` и `X-Content-Type-Options` через meta не работают. На Render их
   можно добавить в *Static Site → Headers*:

   | Path | Header | Value |
   |------|--------|-------|
   | `/*` | `X-Content-Type-Options` | `nosniff` |
   | `/*` | `Referrer-Policy` | `no-referrer` |
   | `/*` | `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=()` |
   | `/*` | `Cross-Origin-Opener-Policy` | `same-origin` |

## Что сделать владельцу проекта

1. **Supabase → Authentication → Sign In / Providers → отключить «Allow new users to sign up»**
   (и вход по email, и анонимный вход, если включены). Игре аккаунты не нужны — Realtime работает с
   publishable-ключом, а открытая регистрация лишь расширяет поверхность.
2. Не выдавать и не вставлять `service_role` / secret-ключ нигде: ни в `.env`, ни в переменные Render и
   GitHub, ни в чат.
3. Переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` задаются в GitHub (Variables) и на
   Render (Environment); обе публичны по назначению.
4. При желании усилить онлайн: приватные каналы Realtime + аутентификация + политики RLS на
   `realtime.messages`. Это следующий шаг, если появится рейтинг или призы.

## Как проверить самому

```bash
npm test               # 250+ тестов, включая проверки безопасности (validate, limits, sync, replay, storage, fuzz)
npm run audit:prod     # известные уязвимости зависимостей
npm run build          # сборка; в dist/index.html виден CSP, нет inline-скриптов и data:-шрифтов
```
